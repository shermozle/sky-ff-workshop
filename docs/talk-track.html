Feature flag fundamentals

10 minutes · Session 00:00–10:00

1Feature flags: the basic idea1 min

Session 00:00–01:00Spend 1 min · move on by 01:00

Start on the slides, with the app closed or in another tab. Say: “Before we touch Amplitude, let’s agree on what a feature flag actually does. It is a named decision our application checks while it runs. We deploy the code that supports a change, then use configuration to decide when and for whom that change is released.” Give the room the shape of the session: concepts, a short demonstration, hands-on practice, then Sky’s architecture discussion.

Keep the explanation concrete; use the recommendation rail as the running example.

2Deploy code; choose when to release it2 min

Session 01:00–03:00Spend 2 min · move on by 03:00

Say: “Imagine we have built a new recommendation-ranking strategy. We can deploy it alongside the existing strategy while keeping everyone on the existing one. The flag lets us release the new strategy to a test audience, then expand that audience. Switching the flag off selects the existing strategy again.” Explain that a flag is not a remote code installer. Ask: “Could you deploy on Tuesday and release to viewers on Thursday?” Answer yes, provided both paths and the flag check are already deployed.

Keep the explanation concrete; use the recommendation rail as the running example.

3What can a flag control?2 min

Session 03:00–05:00Spend 2 min · move on by 05:00

Walk through Sky’s backend use cases first. Say: “A flag doesn’t have to control a button. It can select an algorithm, an API implementation or how a content rail is assembled. The same idea works in a TV client or browser.” Keep the distinction between behavior and audience clear: code knows how to build the rail; the flag’s rules decide which users receive that behavior. Authoritative subscription checks remain in their normal systems; a demo flag is not a replacement for entitlement enforcement.

Keep the explanation concrete; use the recommendation rail as the running example.

4The parts of a feature flag2 min

Session 05:00–07:00Spend 2 min · move on by 07:00

Say: “A variant is one of the possible results of evaluating a flag. In our app, on selects the new recommendation rail and off selects the existing rail. The code decides what each result means; the targeting and allocation decide who receives it.” Then explain the other parts: the key is the stable identifier code requests, and user context supplies identity and relevant properties. A variant can also carry a JSON payload such as a heading or item limit, but the application must be written to use it. Variants are not exclusive to experiments. An experiment might use control and treatment to represent the existing and new ranking strategies. We will connect flags and experiments after explaining evaluation. Percentage allocation uses an identity and configuration rather than a fresh coin toss on every visit.

Keep the explanation concrete; use the recommendation rail as the running example.

Architecture and delivery

10 minutes · Session 10:00–20:00

6What is a deployment?2 min

Session 10:00–12:00Spend 2 min · move on by 12:00

Say: “Here, deployment means a named group of flags that an application or service can access. Our browser app uses sky-workshop-web. When we initialise its SDK with that deployment’s key, Amplitude knows which linked flags are available.” Explain that a deployment belongs to one Analytics project. A project can have multiple deployments, such as web, a TV client, and a recommendation service. The same flag can be attached to multiple deployments when those integrations need it. Give the workshop consequence: every participant attaches their flag to sky-workshop-web; entering a correct flag key in the app is not enough if the flag is missing from that deployment. All 19 participants can share this deployment; they do not need one each. Creating a deployment in Amplitude does not deploy application code or create a hosting server. Its type determines which SDK and deployment key to use: client for a browser, server for a backend.

7The three keys used by this app2 min

Session 12:00–14:00Spend 2 min · move on by 14:00

Say: “There are three different things we have called a key. The flag key is just the decision’s identifier: presenter-recommendations. Each participant creates their own. The client deployment key is shared application configuration: it connects the browser SDK to sky-workshop-web. The Analytics API key sends our fictional profiles and events into the right Analytics project.” Give a question for each: flag key means which decision; deployment key means which group of available flags; Analytics API key means which project receives data. Both browser keys are intended to be visible in client applications. They do not let a participant manage flag configuration. Call out the SDK naming trap: the apiKey parameter of Experiment.initialize expects a deployment key, not the Analytics API key. The numeric project ID and organisation ID identify resources for administration; attendees select Feature Flag workshop by name. A management flag ID used in API URLs is different from its runtime flag key.

Use the three “which?” questions; the detailed key reference remains linked from the workshop.

8Local and remote evaluation2 min

Session 14:00–16:00Spend 2 min · move on by 16:00

Refer back to the evaluator box in the previous diagram. With local evaluation, that box sits inside the SDK runtime, which can be a backend service. With remote evaluation, that box sits at Amplitude and the caller fetches a result. Server-side code can use either mode. Explain that remote enrichment can use stored Analytics properties, while local evaluation needs the relevant inputs available locally or supported sync configuration. The static app will demonstrate remote evaluation; it does not benchmark a server SDK.

9Three operations, three timings1 min

Session 16:00–17:00Spend 1 min · move on by 17:00

Explain the three operations using the slide before opening the app. A remote fetch includes network and SDK work. A variant read retrieves a result already stored by the client. A local evaluation executes targeting logic against available user data and downloaded configuration. We will observe fetch and cached-read timings in the app later; neither is a benchmark of Sky backend local evaluation.

10Caches have different jobs1 min

Session 17:00–18:00Spend 1 min · move on by 18:00

Explain that browser cached reads are different from CDN response caches. Do not promise instantaneous rollback everywhere. In this app the attendee must click Evaluate flags after editing a remote flag. Polling, startup and refresh behavior depend on the chosen SDK and integration.

11Design latency and failure behavior1 min

Session 18:00–19:00Spend 1 min · move on by 19:00

For recommendation services, ask if a default rail is acceptable during an outage. This app discards the prior identity’s decision and shows the default during a fetch or on failure. Other production systems may choose last-known-good for the same identity; that is an explicit engineering choice.

12Rollout and rollback need observation1 min

Session 19:00–20:00Spend 1 min · move on by 20:00

Experiments and APIs

5 minutes · Session 20:00–25:00

13Flags can deliver experiments2 min

Session 20:00–22:00Spend 2 min · move on by 22:00

Say: “Yes, a feature flag can be the delivery mechanism for an experiment. Both use the same ingredients: a key, variants, targeting and allocation. The difference is what we are trying to do with them.” Give two Sky examples. “If I give the new rail to high-engagement viewers and increase the rollout as we gain confidence, I am managing a release. If I randomly assign eligible viewers to the existing rail or the new rail, measure playback starts and watch guardrails, I am running an experiment to learn whether the change helps.” Explain that a 50% rollout by itself does not provide an experiment plan, meaningful exposure tracking or a causal conclusion. Amplitude flags and experiments share an underlying data model and can be migrated between the two types; the experiment interface adds planning, metrics and analysis. The runtime code still reads a variant. Be careful when migrating: keep the key and supported variant values aligned with the application, or update the application. Our workshop app recognises on as the new rail; it will not automatically interpret treatment as on. Say: “Variants describe the experiences we can deliver. The experiment measures the effect of delivering them.”

14Keys kept outside the browser1 min

Session 22:00–23:00Spend 1 min · move on by 23:00

Before showing the API calls, separate reading runtime decisions from changing configuration. Say: “A backend uses a server deployment key to evaluate flags. A CI script uses a management API key to change the flag itself. These keys do different jobs and must stay out of a browser.” The Analytics project secret key belongs to protected Analytics APIs and is another separate credential. None of these three secrets is configured in the static workshop app. The browser’s client deployment key cannot substitute for the management key in the create or disable examples. Project IDs, flag IDs, flag keys and deployment names are identifiers; a privileged API operation still needs its own authorised credential.

Keep the runtime-versus-management distinction; direct detailed questions to the key reference.
