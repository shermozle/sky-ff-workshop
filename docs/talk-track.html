How flags work

15 minutes

3A flag is a runtime decision05:00

Use recommendation-rail as the example. The on variant selects a different fictional rail. A configuration change controls existing code; a flag cannot install missing behavior or undo a destructive data migration.

4Configuration and evaluation are separate07:00

A deployment groups flags delivered to a particular integration. In the workshop all participant flags join the web client deployment. A server deployment would belong to the backend service. A flag key and a management API flag ID are different identifiers.

5Local and remote evaluation09:00

Draw a backend boundary verbally: a server can ask Amplitude for a remote result or evaluate locally with prefetched configuration. This static app demonstrates remote evaluation; it does not benchmark a server SDK. Local cohort support depends on SDK and setup; avoid claiming that every targeting capability is identical.

6Three operations, three timings12:00

Use the inspector. Its fetch timer includes SDK processing; its cached-read timer wraps variant access. It cannot tell whether Amplitude served a CDN hit. Browser timings are not an estimate of Sky backend p95 or p99 latency.

7Caches have different jobs14:00

Explain that browser cached reads are different from CDN response caches. Do not promise instantaneous rollback everywhere. In this app the attendee must click Evaluate flags after editing a remote flag. Polling, startup and refresh behavior depend on the chosen SDK and integration.

8Design latency and failure behavior16:00

For recommendation services, ask if a default rail is acceptable during an outage. This app discards the prior identity’s decision and shows the default during a fetch or on failure. Other production systems may choose last-known-good for the same identity; that is an explicit engineering choice.

9Rollout and rollback need observation18:00

Discuss a staged 1%, 10%, 50%, 100% release as an example, not an automatic policy. Verify consistent identities. Reducing allocation and disabling a flag are different actions. A flag controls the new path; it is not content authorisation.

Experiments and APIs

5 minutes

10Flags and experiments share delivery20:00

A release can use the same delivery concepts as an experiment. Turning on a flag does not establish causal impact. For a rail experiment, define exposure at the point the rail is encountered and measure a decision metric such as playback starts with guardrails.

11Manage configuration programmatically22:00

Open api-examples.html. Walk through a list, create and disable call. The create example associates a flag with a deployment but leaves activation to an explicit step. Management API access requires a separate management key, not either browser key. Runtime REST examples require a server deployment key. No participant runs these privileged calls.

Cut point: show the list and disable calls only; the full examples remain in the guide.
