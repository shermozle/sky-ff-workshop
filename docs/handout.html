Demonstration and setup · 5 minutes

Watch the presenter compare Aroha and Casey after the introductory slides, then open your own workspace.

  1. Open Sky Lab and the dedicated Amplitude project Feature Flag workshop in the Sky NZ organisation (74301). The presenter will provide the project link.
  2. Choose a unique participant prefix, such as alex-t. Your first flag key will be alex-t-recommendations. Avoid shared names.
  3. In the app select Live · Amplitude US. If the connection is not deployed yet, the presenter can supply public browser keys through Live connection settings. Enter only the approved client deployment key.
  4. Choose Aroha and Send identity + profile properties. Keep the optional promo key empty.

Done when: you can find the app, your viewer and the dedicated project.

If you do not have flag creation or activation permission, pair with another participant or use the presenter’s flag. Do not edit another participant’s flag.

Station 1 · Create and target · 12 minutes

  1. In Amplitude, open Experiment → Feature Flags → Create a Feature Flag. Confirm project Feature Flag workshop.
  2. Create your flag with the unique key alex-t-recommendations, replacing alex-t with your prefix. Choose Remote evaluation. Keep the workshop’s consistent user bucketing settings; do not change the salt.
  3. Check that the enabled variant value is exactly on. Attach the shared sky-workshop-web client deployment, or the name supplied by the presenter.
  4. Initially allocate 100% of users to on, save and activate the flag.
  5. Paste the flag key into the app and click Evaluate flags. Aroha should see “Picked for Aroha”.
  6. In Amplitude, replace the all-user rollout with a target segment: subscription_packages contains Sky Sport. It is an array property; select the UI’s appropriate membership operator. Allocate 100% of the matching segment to on, with all other users off. Save changes.
  7. Back in the app, evaluate Aroha, Ben and Dev individually. Selecting a viewer or using Next viewer automatically clears the prior identity and evaluates the selected viewer’s flags, including when returning to someone viewed before. Use Evaluate flags to refresh after editing rules in Amplitude without changing viewers.

Done when: Aroha and Dev receive on; Ben sees “Popular this week”.

The new rail’s titles vary by the selected viewer’s local fixture. The flag decides whether the new rail is used; Amplitude is not generating recommendations.

Station 2 · Rollout and rollback · 10 minutes

  1. Remove the subscription segment. Configure a 50% rollout across all users. Save, keeping the same bucketing unit and salt.
  2. Evaluate each viewer and note the result. Re-evaluate one viewer. Stable identity and unchanged rules should give a stable assignment; five viewers need not split evenly.
  3. Click Copy scenario link. Paste it into Incognito or a private window. Compare the viewer ID and flag key before evaluating.
  4. If the connection keys have not been deployed as defaults, enter the approved client key again in that private window. Connection settings in local storage are not shared with Incognito.
  5. Confirm the same identity gives the same result, then explicitly select another viewer. Incognito by itself is not a new synthetic identity.
  6. Disable the flag in Amplitude, save, then evaluate again in both windows. The app does not automatically poll remote decisions.

Done when: both windows show the default rail after the rollback and a fresh evaluation.

Use Read cached decision to observe a variant lookup without a fetch. It reads the last decision and will not discover a newly changed rule.

Station 3 · Use Amplitude user data · 13 minutes

  1. Reactivate your flag. Remove previous targeting and rollout settings. Add one segment: engagement_level equals high. Allocate matching users 100% to on, everyone else off.
  2. In the app choose Send identity only · use Amplitude profile.
  3. Select Aroha, evaluate, and expand Request inputs. The request contains user_id and device_id, with no targeting property values. The SDK may include an empty user_properties: {} object and library metadata.
  4. Select Casey. The app evaluates automatically; compare the results.
  5. In Amplitude Analytics, inspect the seeded profiles using the exact user IDs above. Verify Aroha has engagement_level: high and Casey has low. The app’s Selected profile fixture panel shows expected local data, not the stored Amplitude profile.
  6. Explain the request path: browser → Amplitude remote evaluation → historical user enrichment → variant response → app rail.

Done when: Aroha receives on, Casey sees the default rail, and neither evaluation request includes profile properties.

Pre-seeded properties can take time to become available for enrichment. This exercise is not a live profile-update race. In practice mode, historical targeting uses simulated profile data; it does not prove that Amplitude has those properties.

Station 4 · Optional promo flag · buffer time

  1. Create alex-t-promo as a second remote flag, with the on variant and the same client deployment.
  2. Target Sky Movies subscribers at 100%, leaving everyone else off.
  3. Enter the second key in the app’s optional promo field. Evaluate Ben and Aroha.
  4. Copy the scenario URL. Both flag keys should be preserved.

Done when: Ben sees “Your next favourite starts here”; Aroha sees the original hero message.

Skip this station if you need more time for the three core exercises.

Troubleshooting

SymptomCheck
No returned flag entryExact key, correct project, deployment association, remote mode, activation and targeting. A missing entry is displayed using the default path.
Live fetch failedUse a client deployment key in the US project. Check network access to Amplitude, browser blockers and the activity log. The previous result is discarded.
Rules changed; UI did notClick Evaluate flags. A cached read makes no request. Allow for propagation; inspect the returned variants.
Historical users all offConfirm the seed ran in this project, exact IDs match, property spelling and type match, and enrichment is ready. Use explicit inputs as a fallback and tell the presenter historical targeting is not yet verified.
Same Incognito resultThe URL preserves identity intentionally. Select another viewer to test a different identity.
Practice results differ from livePractice uses a separate demo hash and local rules. It does not reproduce Amplitude’s assignment algorithm.
Analytics events missingOptional demo tracking is off by default. It needs the Analytics API key and the tracking checkbox. Failures are logged separately from decisions.
